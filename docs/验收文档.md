# 0. 全局 BeUI 复用硬规则

本轮验收新增以下全局硬规则，适用于第 1～6 章全部前端整改。

## 0.1 官方来源优先级

凡 BeUI 已提供官方组件或 Motion primitive，必须按以下顺序使用：

1. **优先使用 BeUI 官方 shadcn registry Install / CLI**
2. 若 registry 无法满足当前工程接入，再使用 BeUI 官方 Manual 源码**原样复制**
3. 只允许做接入 MU 所必需的最小适配
4. **禁止根据 BeUI 页面效果自行仿写**
5. **禁止把 BeUI 官方源码“简化”“优化”“重构”为 MU 自有版本**

BeUI 官方组件是 copy-paste / shadcn registry 分发模式。安装后源码进入 MU 仓库，不构成运行时对 beui.dev 的依赖。

## 0.2 允许修改的范围

仅允许：

- import path / alias 等工程接入调整；
- Vite / React 环境所必需的机械适配；
- MU 业务状态到 BeUI props 的映射；
- 后端接口、controller、ViewModel 与组件之间的业务连接；
- BeUI 官方公开 props / `className` 扩展点允许的**最小业务语义扩展**；
- 本文明确批准的例外，例如 `停止服务` 的 destructive semantic token 覆盖；
- Theme Toggle 中因 MU 已确定不使用 `next-themes` 而必须替换的主题状态桥接。

## 0.3 禁止修改的范围

除非后续验收文档明确批准，否则不得修改 BeUI primitive 内部：

- DOM 层级；
- Tailwind class；
- variant 样式；
- size 样式；
- hover；
- press / tap；
- spring；
- easing；
- duration；
- width morph；
- icon transition；
- loading / success / error 动画；
- reduced-motion；
- View Transition 动画；
- Toast layout / swipe / status morph；
- 官方默认参数。

尤其禁止“看起来差不多”的 MU 自制实现。

## 0.4 关于 BeUI 官方源码中的复杂 DOM

BeUI 官方组件内部为了 Motion 需要，可能主动把字符串拆成多个 `span / motion.span`。

例如官方 `StatefulButton` 会对字符串执行逐字拆分，用于：

- cascade；
- stagger；
- blur / roll；
- 宽度测量与 morph。

因此：

> **不得因为 DOM 看起来复杂，就自行删除或简化 BeUI 官方结构。**

验收判断标准不是“DOM 简单”，而是**是否严格来自 BeUI 官方源码**。

## 0.5 Dashboard 一级分区间距

本轮验收新增全局布局规则：

> **Dashboard 一级分区之间统一保持 32px 垂直间距。**

适用关系：

```text
网站标题区
    ↓ 32px
筛选菜单区
    ↓ 32px
KPI 卡片区
    ↓ 32px
图表区
    ↓ 32px
Session 记录区
```

最终要求：

- 标题栏 → 筛选区：32px；
- 筛选区 → KPI 卡片区：32px；
- KPI 卡片区 → 图表区：32px；
- 图表区 → Session 列表区：32px。

### 实现方式

BeUI 没有要求通过独立的 `margin` 系统控制页面级 section rhythm；其组件与示例直接使用 Tailwind 布局 spacing utilities。

MU 顶层 Dashboard 推荐统一使用父级纵向布局：

```text
display: flex
flex-direction: column
gap: 32px
```

Tailwind：

```text
gap-8
```

即由一个父容器统一控制一级分区间距，而不是让每个一级 section 分别维护：

```text
mt-4 / mt-8 / margin-top: ...
```

整改后应删除 / 取消会与父级 `gap-8` 叠加的一级 section 外部 margin。

### 当前验收

- 标题栏 → 筛选区：目标 32px；
- 筛选区 → KPI：目标 32px；
- KPI → 图表：当前未达到，现有图表 section 使用 16px 级别间距；
- 图表 → Session：当前未达到，现有 Session section 使用 16px 级别间距。

**全局一级分区间距：不通过，统一整改为 32px。**

- 不另造与 BeUI 平行的主题色体系。

### 当前验收

**通过。**

当前版本的基础 semantic token 与 BeUI Neutral 色调方向符合要求。

目前观察到的主要问题不在基础色板本身，因此不要求重新设计整套颜色系统。

## 1.4 亮暗主题状态逻辑

### 设计要求

- 仅支持 `dark` / `light`。
- 默认 Dark。
- 不支持 System。
- 用户选择本地持久化。
- 根节点 `.dark` 驱动主题。

### 当前验收

**通过。**

当前主题状态模型、Dark 默认、本地持久化及 `.dark` 驱动方式符合要求。

## 1.5 亮暗主题切换动画

### BeUI 来源

必须使用：

- BeUI `ThemeToggle`
- `variant="circle-blur"`
- BeUI Theme Toggle 内置 View Transition
- BeUI `ActionSwapIcon`
- BeUI 原生 reduced-motion / unsupported fallback

官方组件：
`https://beui.dev/components/motion/theme-toggle`

官方 registry：
`@beui/theme-toggle`

### 最终验收要求

Reveal 起点必须使用 BeUI 官方示例的：

```text
start = bottom-up
```

对 Circle / Circle Blur 而言，对应屏幕底部中间：

```text
50% 100%
```

即：

- 新主题从**屏幕底部中间**扩张；
- 保留官方 blur → clear；
- 保留官方 duration / easing；
- 保留官方 View Transition；
- reduced-motion 时按官方逻辑直接切换；
- 浏览器不支持 View Transition 时按官方逻辑直接切换。

### 当前实现

当前使用：

```tsx
<ThemeToggle variant="circle-blur" start="top-right" ... />
```

### 验收结论

**不通过。**

当前起点是右上角，与最终要求不符。

整改后必须为：

```text
variant = circle-blur
start   = bottom-up
origin  = 50% 100%
```

不得继续使用 `top-right`。

## 1.6 首次页面主题

### 当前问题

当前 `index.html` 初始根节点没有预先设置 `.dark`，主题 class 主要由 React `ThemeProvider` 挂载后的 effect 应用。

由于：

- 默认主题为 Dark；
- `:root` 对应 Light；
- `.dark` 才对应 Dark；

因此首次打开时存在先绘制 Light、随后再切到 Dark 的首帧闪烁风险。

### BeUI / MU 边界

此处不是 BeUI 视觉组件问题，而是 MU 的主题 bootstrap 问题。

允许 MU 自定义，但只能做**首次主题确定所必需的最小逻辑**。

### 验收结论

**不通过。**

整改要求：

- 在页面首次可见绘制前完成本地主题解析；
- 无本地记录时直接以 Dark 首帧呈现；
- 有合法 `light` 记录时直接以 Light 首帧呈现；
- 不等待 React `useEffect` 后才完成首次主题 class；
- 不产生 Light → Dark 或 Dark → Light 的启动闪烁；
- 不引入 System theme。

## 1.7 字体

### 字体家族

**通过。**

继续使用 JetBrains Mono 及既有 fallback。

### 字重 / 字号 / 行高 / tracking

**本章不判定。**

后续在：

- 网站标题区；
- 筛选与 KPI；
- Session 列表；
- Drawer；

- variant；
- size；

- background；
- radius；
- padding；
- gap；
- font size；
- font weight；
- hover；
- hover lift；

- spring；
- loading；

### 关于逐字 `span`

BeUI 官方 `StatefulButton` 本身会把字符串逐字拆分。

因此：

- **逐字 DOM 不是验收失败原因**；

- 真正的验收要求是：这套结构必须来自 BeUI 官方源码，而不是 MU 自己仿写。

## 2.10 停止服务按钮

## 4.4 `manualSort`

`manualSort` 是 MU 必需的最小 Table 扩展。

BeUI 默认行为是：

```text

```

```text

→ 截取当前页 15 条
```

## 4.18 Table 高度：按当前页实际行数自适应

### 本轮新要求

Ready 状态下按当前页实际 Row 数计算：


最大 15 Row：

```text
48 + 15 × 48 = 768px
```

示例：

```text
15 rows → 768px
10 rows → 528px
3 rows  → 192px
```

- 最后一页少量 Session 时不留下巨大空白；
- 单页最多仍为 15 条；
- 不因为 Table 固定 viewport 再出现无意义纵向滚动；
- 使用 BeUI 已有 `height` prop 动态传值；
- 不修改 BeUI Table 内部源码实现自适应。

Loading / Empty 状态可按对应 Skeleton / Empty 结构单独确定合理高度，但不得回到“固定 16 行空壳”。

**不通过，需改为自适应高度。**

# 6C. Skills 数据正确性修复

## 6C.1 当前现象

用户确认：当前 Skills Used 显示的 Skill 总调用数和 Skill 种类明显少于实际。

这不是仅由前端 Top 10 + Other 引起。Top 10 之外的调用仍聚合进 Other，7d total 也仍应计入全部事件。因此“总次数明显偏少”必须追到后端 Skill recognition。

---

## 6C.2 根因：v0.1.3 → 当前版本收紧过度

v0.1.3 Skill parser 的特点：

- 处理 `response_item`；
- 对合法 `*_call` tool-call 类型具有较宽兼容；
- 在 tool-call payload 内递归寻找 locator 字符串；
- 找到 `SKILL.md` 后取前一级目录作为 skill name。

优点是召回率较高；缺点是可能把普通字符串误识别为 Skill，例如历史已确认 false-positive `const r`。

当前版本为防止误报，将规则收得过窄：

- 只明确处理 `custom_tool_call / function_call / local_shell_call`；
- 只扫描少量固定字段，如 `input / command / cmd / path / file_path / skill_path / action.command / action.cmd`；
- locator 又要求近似 `.../skills/<skill-name>/SKILL.md`，即 skill-name 前一层直接就是 `skills`。

结果是误报下降，但真实 Skill invocation 大量漏报，最终导致 `skill_usage_events`、Skills Used total 和 Skill 种类偏少。

---

## 6C.3 修复原则

不得简单退回 v0.1.3，否则 false-positive 会重新出现。

正确方向：

> **恢复 v0.1.3 的召回能力，同时保留真实 locator 证据约束。**

---

## 6C.4 第一层：tool-call 范围

只处理真实：

```text
response_item
+
tool call
```

不统计普通 message、skills listing / instructions、非 call metadata。

但不再仅枚举当前 3 个 item type，应恢复对合法 `*_call` 类型的兼容，避免 Codex 增加 / 调整 call envelope 后无声漏报。

---

## 6C.5 第二层：只扫描 call 参数树

允许扫描真正属于 tool-call 的 input / arguments / action / command-like payload tree，但不能回到“整个 response_item 所有任意字符串全部扫描”。

尤其不能把 note、message、unrelated metadata 当作 Skill locator 证据。

---

## 6C.6 第三层：Skill locator 结构识别

**不枚举很多具体 Skills 目录。**

禁止维护 `.codex/skills / .agents/skills / .system/skills / .curated/skills ...` 这样的路径白名单。

最终规则：

1. 统一 Windows / Unix 路径：`\\ → /`；
2. 对找到的 `.../SKILL.md`，取前一级目录作为候选 `skill_name`；
3. 继续向祖先路径组件检查；
4. 只要祖先中存在一个完整 path component `skills`，就认为具备 canonical Skill locator 结构；
5. 不存在独立 `skills` component，则拒绝。

概念结构：

```text
... / skills / ... / <skill_name> / SKILL.md
          ↑                 ↑
     存在 skills 层      最后一层为名称
```

可识别示例：

```text
/Users/me/.codex/skills/frontend/SKILL.md
/project/.agents/skills/frontend/SKILL.md
/project/.agents/skills/.system/pdf/SKILL.md
C:/Users/me/.codex/skills/frontend/SKILL.md
```

这些只是结构示例，不是目录枚举白名单。

不应识别：

```text
/tmp/frontend/SKILL.md
/foo/bar/SKILL.md
const r = "SKILL.md"
```

`skills` 必须是完整目录组件，不能因为 `my-skills-backup / skills-old` 等名称而误命中。

skill_name 继续至少校验：非空、不是 `.` / `..`、不含 `/` 或 `\\`、不含控制字符、长度有合理上限。

---

## 6C.7 Parser version / rebuild 闭环

当前 `SKILL_USAGE_PARSER_VERSION = 9`。本修复属于 parser 语义变化，必须升级，例如：

```text
v9 → v10
```

并完成：

```text
Skill parser 修复
↓
parser version / epoch 升级
↓
rebuild skill_usage_events
↓
历史 false-positive 被清理
+
此前漏掉的真实 Skill 被重新捕获
↓
Skills Used 重新聚合
```

不允许只改前端、只加 blacklist、只改 parser 不 rebuild、或保留旧 parser fallback。

---

## 6C.8 数据正确性验收目标

修复后至少验证同一 rolling 7d 窗口：

1. 已知真实 Skill invocation 能进入 `skill_usage_events`；
2. `.codex/skills/.../SKILL.md` 可识别；
3. `.agents/skills/.../SKILL.md` 可识别；
4. `skills` 下存在中间目录时仍可识别；
5. Windows 路径可识别；
6. 普通 `/foo/bar/SKILL.md` 不识别；
7. `const r` 等历史误报不重新出现；
8. Skills Used `7d total` 与重建后的事件数一致；
9. Skill 种类恢复到与真实调用相符的范围；
10. Top 10 + Other 只影响展示分组，不丢事件。

## 1. 产品目标与总体方向

### 1.1 产品目标 【已确认】

- 让用户在 Usagi 看到**通过 agent 产生的一切花费**，并能追溯整个链条：会话 ↔ 主 agent / 子 agent ↔ 请求。
- 这是最终愿景。Magpie 暂时给不出的关系**明确留空，不靠猜测补齐**。

### 1.2 两个视角 【已确认】

- Usagi 分为**会话页**和**请求页**两个标签页，是同一份消耗数据的两个视角，不是两本互不相干的账。
- 两页使用**同一套 Token 定义和同一套计价规则**。
- 用户确定的落地顺序：
  1. 设计会话页（模块与数据）；
  2. 确定会话页每项数据的口径和来源；
  3. 落地会话页；
  4. 最后再做请求页。
- 在讨论第 2 步时，用户提出“必须先讨论更前置的问题”：Usagi 自建数据库（§6）。

### 1.3 数据来源 【已确认】

- **Usagi 的数据来源只有 Magpie。** Magpie 能提供的会话（包括没有经过 Magpie 网关、由本地日志重建的会话）都纳入。用户原话：“要，我们的数据来源是 magpie，它能提供这个信息我们就使用。”
- 后期可以根据需要增加本地扫描作为补充 【暂缓】。

### 1.4 计价 【已确认】

- **费用由 Usagi 自己计算**，不再使用 Magpie 返回的 `cost`。用户原话：“usagi 自己算，实际规则和公式和 magpie 基本是一致的，可以照搬，只是我们放在 usagi 就可以自行决定什么情况下不适用分阶段计费的规则。”
- 此前与 Codex 的梳理中，用户已经确定的口径是：**等价费用 = 各模型、各类 Token × 对应基础单价，不做 272K 分段加价**。本期按“不使用任何分段（Tier）”实施；以后如果要在某些情况下启用分段，由用户再决定。
- **价格更新后，历史费用不变**：每笔请求按其发生时有效的价格版本计算（规则见 §7.3）。
- 未计价模型怎么展示 【暂缓】，到详细数据实现阶段再讨论（数据层的最小处理见 §7.6）。
- 金额单位为美元。

### 1.5 不重复计算 【已确认】

- 会话页顶部汇总按全局去重计算：**每一笔消耗只计一次**。
- 列表每行显示**包含子 agent 的合计**。

## 2. 关键事实（来自 Magpie 实测与源码）

这些事实是后面各项设计的前提。编写方案时不需要再次验证，但如果发现与事实不符，要先停下来报告。

### 2.1 Magpie 的两份数据

| | 请求账本 `/api/usage/requests` | 会话列表 `/api/sessions` |
|---|---|---|
| 粒度 | 每次模型请求一行 | 每个会话一行，只有生命周期累计值 |
| 覆盖 | 网关请求 + Magpie 从各 agent 本地日志重建的请求（`source:"log"`，provider 为 `session-unknown`，约占 86%） | Magpie 发现的全部会话（本机约 1800 条） |
| 去重 | **已去重**：同一次调用的网关行和日志行配对后只保留网关行（Magpie `internal/usage/ledger.go:331-347` 配对，`:362-430` 的 `ledgerMatched` 隐藏已配对的日志行）。配对有歧义时两行都保留 | **未去重**：见 2.3 |
| 时间范围 | 支持 `today/7d/30d/all` 和 `YYYY-MM-DD..YYYY-MM-DD`（本地时区，两端都包含）。`yesterday`、单日 `YYYY-MM-DD`、反序区间都会被静默当成 `30d` | 不支持，只返回累计值 |
| 分页 | 每页最多 500 行，按 `offset` 翻页 | 不分页，`limit=0` 返回全部 |

### 2.2 账本行的特点

- **没有增量游标**（没有 since/after/updated_at）。
- **没有稳定的行 ID**：日志重建的行没有 `route_id`/`response_id`；约 11% 的网关行也没有 `route_id`。
- **行会变化**：网关行晚到时，对应的日志行会被隐藏；Claude 流式响应的用量会被修订；用户删除本地日志后，对应的行会消失。
- 对整个 `all` 范围按 offset 翻页时，翻页期间有新行写入，会导致页边界错位、出现重复行。**按天拉取是稳定的做法。**
- `cost` 在 Magpie 内部不落盘，每次读取时按当前价格表计算。
- 时间戳格式混杂：网关行是 `+08:00`，日志行是 `Z`，表示的是同一时刻体系，需要统一解析。
- 行中**没有工具名字段**。`kind` 表示**这次请求的用途**，不是工具类型。取值见 Magpie `internal/usage/purpose.go:20-30`：
  - 子 agent：`collab_spawn`、`thread_spawn`、`agent_job`
  - 标题：`thread_title`、`thread_title_reconsideration`、`title_generation`、`title`
  - 压缩：`compact`
  - 记忆、审批检查、网页搜索（`web_search`）、输入建议、图片描述、代码审查等
  - 为空：普通对话轮次
- 字段含义：
  - `agent`：发起请求的客户端；
  - `provider`：请求实际发往的上游；
  - `providerAccount`：上游下的登录账号（通常是邮箱）。
- Token 字段关系：`input` 不含缓存读；`reasoning` 已包含在 `output` 中；`cache_write_1h` 是 `cache_write` 的一部分（子集），不能另外相加。

### 2.3 `/api/sessions` 中“不是独立消耗单位”的条目

| 类别 | 数量（快照） | 现象 |
|---|---|---|
| Codex 子 agent | 约 1165 条 | 每个子 agent 是一个独立会话；**接口不提供父会话**（父子关系只在 rollout 文件第一行）。子 agent 自己**没有账本行**，它的消耗在账本里以 `kind=collab_spawn` 记在**父会话 ID** 下。用户已向 Magpie 提 issue |
| 网关空壳会话 | 68 条：Codex 60 条，claude-desktop 8 条 | Codex 的 60 条全部是标题生成请求（`thread_title`），Codex 用单独的线程 ID 发出，没有项目目录，标题等于 ID；它们有自己的账本行。claude-desktop 的 8 条：4 条是下面的同 ID 重复，1 条是不同 ID 的重复，2 条是全部 429 的 Haiku 标题请求，1 条是 Haiku 辅助调用 |
| claude 与 claude-desktop 同 ID 重复 | 4 组 | 本地文件（`claude`）和网关（`claude-desktop`）各一条。按响应 ID 逐条比对：**网关是本地文件的超集**，多出来的是不写进本地文件的辅助请求和 429 失败请求 |
| 不同 ID 的重复 | 至少 1 组（`6bc24346` / `33f4dc97`） | 同一批请求，ID 不同 |
| `claude -p` 子进程会话 | 若干 | 在会话列表里是独立会话（没有自己的账本行），但它的消耗在账本里挂在父会话的 `subagent` 下 |

**由此得出的原则：消耗只从账本行汇总，`/api/sessions` 只提供会话元数据。** 按这个原则，上表所有重复都不会被重复计算。

### 2.4 子 agent 在账本中的表示

- **Claude**：子 agent 的请求带 `subagent`（agent id），`session` 是父会话 ID。子 agent 个数 = 该会话下不同的非空 `subagent` 值个数（`claude -p` 子进程的调用也以这种形式出现，因此也会被计入）。`parent_agent` 在本机数据中全为空。
- **Codex**：子 agent 的请求 `subagent` 为空，用 `kind=collab_spawn` 标记，`session` 是父会话 ID。**无法通过 API 算出子 agent 个数**。

### 2.5 `/api/sessions/overview` 的限制

- 只支持“最近 N 天”（`days=1/7/30/90/0`），**不支持昨天、今年、自定义区间**；`from`/`to` 参数无效。
- 筛选只能单选（agent、model、cwd）；按模型筛选时整个会话一起计入。
- “今天”的日期边界是本地时间还是 UTC，两份调查结论冲突，**实施时需要核实**。
- `tools` 字段：只给前 8 个工具（`top`），以及总调用数 `calls`、分类 `categories`、按周分类 `weeks`。没有按会话、按天的工具数据。工具调用按发生的日期累计，窗口内发生的调用才计入。
- 工具调用来自 Magpie 对会话文件的解析，账本里没有，**Usagi 无法用其他方式自己算**。opencode 的工具调用 Magpie 没有解析。

### 2.6 价格来源

- Magpie **没有自己维护价格表**。它下载 models.dev 的公开数据（`https://models.dev/api.json`），缓存在 `~/.cache/magpie/models.json`（Magpie `internal/catalog/catalog.go:343、382`）。
- models.dev 是一个开源、社区维护的模型资料库（opencode / SST 团队发起），按供应商列出模型单价，单位是美元/百万 Token。
- Magpie 在此之上的规则（`internal/provider/models.go:1131-1156`、`internal/catalog/catalog.go`）：
  - 价格优先级：用户在 Magpie 里自定义的价格 → 供应商目录价 × 供应商倍率 → 模型厂商原价。
  - 1 小时缓存写：models.dev 没有这一项，Claude 模型按输入价的 2 倍补上，其他模型按 5 分钟缓存写价格算（`catalog.go` 的 `OneHourFor`）。
  - 当 `model` 无价而 `served` 有价时，用 `served` 的价格（`ledger.go` 约 437 行附近的注释）。
  - 只有 `input + output > 0` 的行才计费。
  - 分段加价：Usagi 不采用。
  - 单行费用公式（不含分段）：
    ```
    cost = (input×输入价 + output×输出价 + cache_read×缓存读价
            + (cache_write − cache_write_1h)×缓存写价 + cache_write_1h×1h缓存写价) / 1e6
    ```
- Magpie 没有提供价格表的接口；用户在 Magpie 里自定义的价格存在它的 `settings.json` 中，Usagi 拿不到。

## 3. 会话的定义

> **会话 = `/api/sessions` 中的一条会话元数据（同 ID 的 claude / claude-desktop 合并）；它的消耗只从账本行汇总。**

| 规则 | 状态 |
|---|---|
| 会话页以会话为基础单位。只要是 Magpie 提供的会话，无论有没有消耗、有没有计价数据，都收录。用户原话：“以会话为基础原子，无论是不是有消耗的会话、是不是有计费数据，只要它是一个会话，就收录进来” | 【已确认】 |
| Token、费用等消耗**只从账本行汇总**，不使用 `/api/sessions` 的累计值 | 【已确认】 |
| claude 与 claude-desktop 的同 ID 会话合并成一行；标题、项目取本地文件那条 | 【已确认】 |
| 合并后这一行的 Agent 显示 **`claude`** | 【已确认】 |
| 不同 ID 的重复（如 `6bc24346` / `33f4dc97`）不做特殊合并。按“消耗只从账本行算”，没有账本行的那一条不会重复计算 | 【已确认】 |
| 网关空壳会话**放进列表**。标题显示会话 ID，项目显示“无项目”，消耗正常显示并计入 KPI。用户原话：“先放进列表，我后续再优化” | 【已确认】 |
| Codex 子 agent **全部显示为独立行**，直到 Magpie 提供父子关系 | 【已确认】 |
| Codex 子 agent 行的 Token 和费用显示“—” | 【已确认】 |
| 没有会话 ID 的请求（本机约 121 行、约 $2.96）不属于任何会话：不进会话列表，**不计入会话页 KPI 和图表**；到请求页再正常计入 | 【已确认】 |
| 会话页**不显示**“未归入会话的消耗”提示条 | 【已确认】 |

### 3.1 “Codex 子 agent 显示 —”如何落地 【已确认】

通过 API **无法识别**哪些会话是 Codex 子 agent：它们和 `claude -p` 子进程会话、以及确实没有任何消耗的会话一样，都表现为“没有账本行”。因此：

- 用户已确认的“Codex 子 agent 行显示 —”，实施时落到**所有没有账本行的会话**上：Token、缓存率、费用都显示“—”，不显示 0。
- **不加任何提示**，只显示“—”。【已确认】

### 3.2 会话身份与账本行的对应 【已确认】

| 规则 | 说明 |
|---|---|
| 账本行的会话 ID | 取 `native_session`，为空时取 `session`（沿用现状 `internal/query/sessions.go:133-155`） |
| 会话的唯一键 | `(agent 族, 会话 ID)`。`claude` 与 `claude-desktop` 视为同一个 agent 族，其余 agent 各自一族。`sessions` 表可以仍按 `(agent, id)` 存原始元数据，展示和汇总时按 agent 族合并 |
| 账本行 → 会话 | 用 `(行的 agent 所属族, 行的会话 ID)` 匹配会话 |
| 账本里有会话 ID、但 `/api/sessions` 没有元数据 | 仍作为一个会话显示（标题空 → “未命名会话”，项目 → “未识别项目”），计入 KPI。沿用现状（`Matched=false`） |
| 已从 Magpie 消失、但 Usagi 库里还有的会话 | 照常显示，元数据用库里最后一次的值 |

### 3.3 收录范围（结合时间范围和筛选）

| 规则 | 状态 |
|---|---|
| 消耗按账本行时间 `t` 所在的**本地日**计入时间范围；“今天”看到的是今天产生的消耗，不是今天活跃会话的全部历史用量 | 【已确认】（Codex 梳理中确立，用户未改） |
| 范围内有账本行的会话：收录，行内数值只算范围内的部分 | 【已确认】 |
| 收录规则统一为：**范围内有账本行，或 `Session.last` 落在范围内**，二者满足其一即收录。范围内没有账本行的会话（包括“范围外有账本行、`last` 在范围内”的会话），Token、缓存率、费用显示“—”，不计入中位 / P90 | 【已确认】 |
| 筛选作用在**消耗**上：选了模型 X，KPI 和每行都只算 X 的那部分；没有匹配消耗的会话从列表中消失 | 【已确认】 |
| Agent 筛选按 **agent 族**过滤：选 `claude` 即包含 `claude-desktop`；合并会话整行保留 | 【已确认】 |
| 项目的身份按 `cwd` **完整路径**区分，显示最后一级目录名；同名不同路径是两个项目 | 【已确认】 |
| 有模型筛选时，没有账本行的会话（没有模型信息）不收录；Agent 和项目筛选对它们按会话元数据（agent 族、cwd）判断 | 【已确认】 |

### 3.4 失败行

- 被拒绝的行（`rejected`，或 provider 为空且 status ≥ 400）整行剔除；其他失败行照常计入 Token 和会话存在性（沿用现状 `internal/query/usage.go:67-69、175-178`）。【已确认】

| 项 | 结论 | 状态 |
|---|---|---|
| 时间范围 | 今天、昨天、7 天、30 天、今年、自定义，**保持现状**（标签文字也不改，现状为“7d / 30d”） | 【已确认】 |
| 筛选项 | Agent、模型、项目三项 | 【已确认】 |

### 4.2 模块 1：KPI 卡片

**前提 【已确认】：** KPI 卡片展示的是**会话页当前筛选结果**的汇总。

**会话页只放 5 张卡 【已确认】：** 总 Token、缓存命中、等价费用、会话数、账户额度。

**请求数卡 【已确认】：** 代码保留，不删，以后放到请求页；只是不在会话页显示。（当前工作区里会话数卡已被请求数卡替换，需要改回来。）

## 6. 架构：Usagi 自建数据库

### 6.0 与会话页的关系 【已确认】

用户在讨论会话页口径时提出，数据库是“更前置的问题”。因此 SQLite 数据层是落地会话页的**前置交付物**：会话页的 KPI、列表、图表 A 都从 Usagi 数据库计算；图表 B 和账户额度仍实时读取 Magpie。

- 现有的内存缓存 `internal/query/store.go`（按日缓存 + 按日指纹）由新的同步层取代，其中的指纹比对、按天拉取、60 天分块等逻辑可以迁移复用。
- 现有内部 API 的端点和 DTO 哪些保留、哪些调整，由方案给出，并列出前端受影响的地方。

### 6.1 决定

| 项 | 状态 |
|---|---|
| Usagi 建立自己的数据库；后端定期从 Magpie 请求数据 → 存入 Usagi 数据库 → Usagi 自己计算、给前端提供接口；后期可做本地扫描补充（用户提出的方向） | 【已确认】 |
| 选用 **SQLite**（用户提出，Claude 评估认为合适：本机约 16 万请求行、1800 个会话） | 【已确认】 |
| Go 端使用纯 Go 实现的 `modernc.org/sqlite`（不需要 cgo，便于跨平台分发；Usagi 的 Go 重写阶段用过） | 【已确认】 |
| 通过 Magpie 的 HTTP API 同步，**不直接读 Magpie 的磁盘文件**（`usage.jsonl` 只有网关行、没有日志重建行，也没有去重和计价；缓存文件是带版本的 gob，随时失效） | 【已确认】 |

```
Magpie（HTTP API） ──定期同步──▶ Usagi 后端 ──写入──▶ Usagi SQLite
                                                      │
                                    Usagi 自己计算 ◀───┘ ──▶ 接口 ──▶ 前端
（后期：本地扫描作为补充数据源，写入同一个库）
```

### 6.2 数据库能解决和不能解决的问题

| 问题 | 能否解决 | 说明 |
|---|---|---|
| 昨天、今年、自定义范围 | 能 | 请求行存进 SQLite 后可以按任意范围查询 |
| 中位 / P90 | 能 | 用会话汇总自算 |
| 重启后要重新拉全部数据 | 能 | 当前只缓存在内存（`internal/query/store.go`） |
| 历史丢失（用户删除本地日志后 Magpie 不再提供） | 能 | 配合历史冻结（§6.4） |
| 自主计价、价格版本 | 能 | 存原始 Token |
| 复杂查询（合并、多选筛选、关系） | 能 | |
| **Tool 按会话 / 按天统计** | **不能** | Magpie 只提供汇总，需要本地扫描或 Magpie 增加接口 |
| **Codex 父子关系** | **不能** | 等 Magpie issue 或本地扫描 |

### 6.3 吸取的历史教训 【已确认】

Usagi 曾两次自建 SQLite（Rust 版约 23 张表；Go 版 Spec01-04），2026-10-11 改为依赖 Magpie。当时的主要痛点是**自己解析原始日志，并自己保证去重和归属**（Spec04 的 epoch / shadow rebuild 规格约 1350 行，最后在真实数据上卡死）。本次方案的区别和沿用的原则：

- **只同步 Magpie 已整理、已去重的结构化数据，不解析原始文件。**
- 未冻结的数据是**派生数据，可以随时清空后从 Magpie 重建**。冻结的历史（§6.4）无法从 Magpie 重建，清库或库损坏会丢失这部分；**不做备份**。【已确认】
- **不存对话正文。**
- **第一版不建预汇总表**，用索引直接查询；有性能证据后再加。
- 不要重新引入 epoch、shadow build、carry 这类账本协议。

### 6.4 同步方案

| 规则 | 状态 |
|---|---|
| 同步单位是**本地日**：`period=D..D` 分页拉全一天 | 【已确认】 |
| 变化检测：沿用现有的按日指纹（`internal/query/store.go` 已实现；Magpie 只在窗口 ≤60 天时按天给 series，按 60 天分块，`store.go:20`）。指纹里包含 Magpie 的 cost，Magpie 价格表变化也会触发重拉，对未冻结的日期可以接受 | 【已确认】 |
| 某天有变化时，在**一个事务里删除这一天的旧行、写入新行**（整天替换，不做逐行 upsert，以绕开“没有稳定行 ID”和“行会变化”的问题） | 【已确认】 |
| 分页过程中用 `total` 复核；拉取期间 total 变化就重拉整天 | 【已确认】 |
| **历史冻结：超过 7 天的日期冻结**，之后 Magpie 那边的数据再变化，也不覆盖 Usagi 中已有的记录；只记录差异（例如指纹和行数变化） | 【已确认】 |
| 冻结条件：日期早于“今天 − 7 天”，**且**该日结束之后至少成功同步过一次（避免某天只同步了一半就被冻结） | 【已确认】 |
| 首次同步：更早的日期仍需完整拉取一次，拉取后按上面的条件冻结 | 【已确认】 |
| 同步由后端常驻任务执行；Magpie 不可用时，页面继续用库中已有数据展示 | 【已确认】 |
| 首次同步进行中：保持现状，显示骨架屏 | 【已确认】 |
| 同步频率：用量、会话、额度**都改为 60 秒**（现状 30 / 30 / 60 秒，`internal/api/server.go:35-37`） | 【已确认】 |
| 会话元数据 `/api/sessions` 每次全量拉取（约 0.25 秒），按 agent+id upsert；记录首次出现和最后出现时间，Magpie 中已消失的会话保留并标记 | 【已确认】 |
| 冻结后发现 Magpie 有差异：只写入 `sync_days` 并记日志，**界面不提示** | 【已确认】 |

## 7. 价格表

### 7.1 来源 【已确认：方案 c】

**Usagi 自己从 models.dev 拉取价格 + Usagi 内的用户自定义覆盖。** 不读 Magpie 的缓存文件。本期只做 models.dev 部分；Usagi 内的自定义覆盖留到后期价格同步功能（§7.5）。

### 7.2 规则（照搬 Magpie，去掉分段）

| 规则 | 状态 |
|---|---|
| 公式见 §2.6，**不使用 Tier（分段）** | 【已确认】 |
| 1 小时缓存写价格的补齐规则照搬 Magpie（Claude 按输入价 2 倍，其他按 5 分钟缓存写价） | 【已确认】 |
| 优先级：Usagi 用户自定义价格（后期）→ models.dev 价格 | 【已确认】（方案 c） |
| **不提供**与 Magpie “用户自定义价格”“供应商倍率”对应的设置。供应商倍率在 Magpie 中是用户对单个供应商设置的可选值（`internal/provider/provider.go:167-172`，`omitempty`），默认 0，表示不调整（`models.go:1152` 只在 > 0 时才乘）。因此 Usagi 默认倍率为 **1（不调整）** | 【已确认】 |
| 只在 `input + output > 0` 时计费，**照搬** Magpie（`internal/usage/ledger.go:390`） | 【已确认】 |
| `model` 无价时用 `served` 的价格，**照搬** Magpie（`ledger.go` 的 `pricer`） | 【已确认】 |

### 7.3 历史费用 【已确认：方案 a】

- 每笔请求按**发生时有效的价格版本**计算；价格更新后，**历史费用不变**。
- 费用在**查询时**按请求时间查对应的价格版本现算，不入库存储。【已确认】
- 首个价格版本**向前适用**：它生效之前的所有历史请求都按它计算。【已确认】
- 用户自定义价格本期不做，版本语义留到后期价格同步功能再定。【暂缓】

### 7.4 价格查找规则 【已确认：照搬 Magpie，Claude 已读源码】

Magpie 的查价逻辑（`internal/usage/ledger.go` 的 `pricer`，`internal/provider/models.go:1025-1048、1088-1095、1131-1156、1232-1244`）：

1. **先用 `model` 查价**；查不到且 `served` 非空、与 `model` 不同时，**再用 `served` 查价**（同一个 provider）。不使用 `requested`。
2. 用一个模型名查价时：
   - provider 是 Magpie 已知的供应商（如 `claude`、`codex`、`copilot`、`openai`）：先查该供应商对应的 models.dev 目录，查不到再查模型厂商的目录；
   - provider 不是已知供应商（如 `session-unknown`）：直接查模型厂商的目录。
3. 模型名先做少量别名展开再查（`pricedNames`，例如 `codex-auto-review` → `gpt-5.6-luna`）。
4. 都查不到：这一行为**未计价**。
5. Magpie 的用户自定义价格这一步跳过；供应商倍率按 1 处理（§7.2）。

方案实现时直接照这个顺序移植，不另建映射表。如果移植时发现某个供应商到 models.dev 目录的对应关系在 Magpie 里是动态配置的（不是代码写死的），停下来报告。

### 7.5 价格同步功能 【暂缓：后期功能，方向已确认】

- 设置中可以配置**自动同步时间 / 间隔**，并提供“立即同步”。
- 每次同步生成新的价格版本，记录生效时间，并显示与上一版相比哪些模型价格变了。
- 用户自定义价格（届时再做）始终优先，不会被同步覆盖。

### 7.6 本期价格数据的最小实现 【已确认】

- Usagi **首次启动时**从 `https://models.dev/api.json` 拉取一次，生成第 1 个价格版本（向前适用，§7.3）。之后在自动同步功能（§7.5）上线前不再自动更新。
- 拉取失败时：不生成版本，下一个同步周期（60 秒）重试；在有价格版本之前，所有行按未计价处理。
- 未计价的行：费用按 **0** 参与合计，并单独计数（与 Magpie 一致），所以“KPI = 列表之和”仍然成立。未计价的展示方式【暂缓】。
